# 구현과 분석의 연결

## 현재 웹에서 실행하는 경로

`app.py`가 두 PDF를 작업 폴더에 저장하고 순차 실행 풀에서 `scripts/worker.py`를 별도 프로세스로 실행합니다. 작업 상태와 로그는 로컬 작업 폴더에 남기며 실제 진행 단계와 실패를 표시합니다. Windows 파일 공유 잠금에 대비해 JSON 저장을 재시도합니다.

Worker는 두 기간에 대해 재무 표 추출, 문서 텍스트 추출, Kiwi 텍스트 분석, 카테고리 매핑과 재무 표 구조화를 수행합니다. 이어 변화 탐지, 우선순위, 규칙 분석, 근거 데이터 구성, 문단 구성, 계정 비교와 viewer JSON 구성을 실행합니다. 은행 거래 데이터 모듈을 현재 웹에 연결해 개별 기업을 검증하는 흐름은 아닙니다.

`review/adapter.py`는 기존 viewer 결과를 문단·문자열 위치·검토 항목으로 바꿉니다. `enrichment.py`는 PDF 페이지 후보와 명시된 전기·당기 열의 금액 비교를 추가합니다. `financial_guide.py`는 정확한 금액 비교 문장과 계정별 검토 질문을 구성합니다.

`connections.py`는 사전·명시적 계정 키워드로 다른 문맥과 계정을 찾습니다. 검색에 사용한 키워드·총 후보 수·표시 수를 구분하며, 연결은 동일 거래나 인과관계의 증명이 아닙니다. 은행 데이터가 필요한 확인사항은 추가 자료 필요로 반환합니다.

`explanation.py`는 문맥·연결 근거와 일반 개념 출처를 LLM에 전달합니다. 응답 스키마는 간결하게 보내고, 구조·길이·인용·출처·숫자 조건은 로컬에서 검증합니다. 문서 내부 명령은 인용 자료로 취급하도록 지시하지만 프롬프트 지시와 형식 검증만으로 모든 생성 오류를 막을 수는 없습니다.

`web/`은 네 문서 탭, 하이라이트, 요약 카드, 확인사항 탐색, 검토 메모와 보고서 출력을 담당합니다. `report.py`는 담당자 상태와 메모, 근거·생성 설명을 HTML 스냅샷으로 구성합니다. 원본 PDF에 좌표 하이라이트를 덧씌우는 구현은 아닙니다.

## 기존 분석과 현재 화면의 차이

| 항목 | 기존 분석 | 현재 화면 |
|---|---|---|
| 표현 집계 | Kiwi 명사·N-gram·카테고리 행 기반 | 화면 추출 문단의 비중첩 사전 문자열 일치 |
| 우선순위 | 생성·소멸·횟수 변화량을 더한 규칙 점수 | 변화별 종류 카드와 위치 선택, 담당자 상태 필터 |
| 재무 비교 | 기존 계정 구조화·비교·규칙 근거 | 명시된 전기·당기 열 재검산, 단위 검토, 코드 요약 |
| 설명 | 기존 생성 모듈 | 별도 출처·인용·숫자 검증을 적용한 선택 근거 설명 |
| 저장 | 발표자료에는 DB 설계도 포함 | 현재 앱은 작업별 파일·JSON 저장 |

## 포함된 역사적 코드의 범위

`legacy/`에는 기존 파이프라인과 사전의 복사본을 남겼습니다. 이 폴더의 모든 모듈이 현재 웹에서 호출되는 것은 아닙니다. 은행 데이터 비교·이전 LLM 모듈은 현재 서비스의 검증된 기능으로 소개하지 않습니다. 은행 데이터 모듈의 개인 절대경로는 공개본에서 상대경로로 치환했고 실제 데이터는 포함하지 않았습니다.

표 추출 모듈에는 선택적인 PDF 이미지 변환 코드도 남아 있습니다. 현재 검증 경로는 PDF 구간을 Gemini에 전달하는 방식입니다. 사용하지 않은 이미지 변환 도구나 Vertex AI 전용 SDK를 필수 기술로 추가하지 않았습니다.

## 왜 학습형 위험 분류 대신 규칙인가?

이번 구현의 목표는 위험 여부 예측 성능 경쟁이 아니라 검토할 위치와 확인 이유를 제공하는 것입니다. 사전·규칙은 담당자가 근거를 확인하고 수정할 수 있습니다. 반면 부정문·동의어·오탈자와 도메인 변화에 약하므로 정답 라벨을 구축한 뒤 누락과 과탐을 평가해야 합니다.

확인 완료는 담당자의 기록 상태이며 자동 판정이나 모델 신뢰도가 아닙니다. 하이라이트, 요약, 관련 근거 탐색, 실제 판단의 역할을 분리해 설계했습니다.
